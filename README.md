# Ассистент анализа пользовательских отзывов: One-shot vs Sequential Workflow

## 1. Название и краткое описание проекта

**Название:** Review Analyzer (DeepSeek API).

**Назначение:** автоматический анализ текста пользовательского отзыва с выдачей структурированного результата для бизнеса.

**Входные данные:** текст отзыва на русском языке (строка `review_text`).

**Выходные данные (структура):**

| Поле | Тип | Описание |
|---|---|---|
| `overall_sentiment` | `str` | Общая тональность: `positive / negative / neutral / mixed` |
| `aspects` | `List[dict]` | Аспекты: `name`, `sentiment`, `evidence` |
| `summary` | `str` | Краткое резюме (1–2 предложения) |
| `business_recommendation` | `str` | Рекомендация для бизнеса |

**Основные операции (LLM):**
1. Извлечение аспектов (тем) из отзыва.
2. Классификация тональности (общей и по каждому аспекту).
3. Генерация резюме и рекомендации.

**Сценарии использования:** автоматическая обработка потока отзывов с маркетплейса; ежедневная сводка для продукт-менеджера; приоритизация негативных отзывов для службы поддержки.

**Возможности расширения:** RAG для рекомендаций на основе базы знаний, интеграция с CRM, агентная проверка фактов в отзыве.

> **Примечание по API.** По заданию требовалась реализация через OpenRouter. Из-за отсутствия VPN доступ к OpenRouter получить не удалось, поэтому используется **DeepSeek API** (OpenAI-совместимый, `base_url="https://api.deepseek.com"`, модель `deepseek-chat`). Структурированный вывод реализован через JSON Output (`response_format={"type": "json_object"}`). Функционально решение полностью соответствует заданию: те же две архитектуры, те же операции, тот же формат результата.

## 2. Описание выбранной архитектуры

Реализованы **две архитектуры**, которые сравниваются на одинаковых входных данных.

### 2.1. One-shot (baseline)

Один LLM-вызов, в котором промпт охватывает все операции сразу и требует вернуть JSON по заданной схеме. Реализация — `src/one_shot.py`.

### 2.2. Sequential Workflow

Два последовательных LLM-вызова:

- **Шаг 1 — Extraction:** извлечение аспектов из отзыва (`name`, `quote`). Результат — `ExtractionResult` (Pydantic-модель).
- **Шаг 2 — Classify & Summarize:** на вход подаётся отзыв + структурированный список аспектов; на выходе — `ReviewAnalysis` (тональность каждого аспекта, общая тональность, резюме, рекомендация).

Между шагами данные передаются в виде Pydantic-моделей (`src/models.py`), что обеспечивает валидацию и структурированность.

**Схема:**

```
                  ┌─────────────────────┐
                  │  Входной отзыв      │
                  └──────────┬──────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
   ┌─────────────────────┐       ┌─────────────────────┐
   │     ONE-SHOT        │       │     WORKFLOW        │
   │  (1 LLM-вызов)      │       │  (2 LLM-вызова)     │
   │                     │       │                     │
   │  промпт «всё сразу» │       │  Шаг 1: Extraction  │
   │                     │       │  (аспекты + цитаты) │
   │                     │       └──────────┬──────────┘
   │                     │                  │ structured JSON
   │                     │                  ▼
   │                     │       ┌─────────────────────┐
   │                     │       │  Шаг 2: Classify    │
   │                     │       │ (тональность +      │
   │                     │       │  резюме + рекоменд.)│
   └──────────┬──────────┘       └──────────┬──────────┘
              │                             │
              ▼                             ▼
   ┌─────────────────────────────────────────────────┐
   │         ReviewAnalysis (Pydantic)               │
   │  overall_sentiment, aspects[], summary,         │
   │  business_recommendation                        │
   └─────────────────────────────────────────────────┘
```

**Обоснование выбора Sequential:**
- Результат шага 1 (список аспектов) логически необходим шагу 2 — это соответствует паттерну Sequential.
- Декомпозиция снижает нагрузку на модель: на каждом шаге решается одна узкая задача.
- Ошибки локализуемы: видно, на каком шаге они возникли.
- Архитектура расширяема: можно добавить шаг валидации аспектов или Routing перед workflow.

**Обработка ошибок:**
- Сетевые ошибки и ошибки API — retry (до 2 повторов) в `src/llm_client.py`.
- Невалидный JSON или пустой ответ — повторная попытка, затем fallback-объект `ReviewAnalysis` с нейтральными значениями, чтобы пайплайн не падал.
- Ошибка шага 1 workflow — деградация до пустого списка аспектов; шаг 2 всё равно выполняется.
- Ошибка шага 2 — возвращается безопасный fallback с пометкой «Требуется ручная проверка».

## 3. Инструкции по запуску

### 3.1. Установка

```
git clone git@github.com:DiHASTRO/great-generative-models-automatization.git
cd great-generative-models-automatization
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 3.2. Настройка ключа

```
cp .env.example .env
```

Отредактируйте `.env`, указав `DEEPSEEK_API_KEY`. Ключ хранится только в `.env` или переменной окружения. `.env` добавлен в `.gitignore`; в сдаваемых файлах секретов нет.

### 3.3. Запуск эксперимента

```
python -m src.evaluate
```

Запускать **из корня проекта** (там, где лежат `src/`, `data/`, `.env`). Скрипт читает `data/test_cases.json`, прогоняет каждый кейс через обе архитектуры, считает метрики, выводит сводку в консоль и сохраняет `results_summary.json`.

### 3.4. Структура проекта

```
review-analyzer-deepseek/
├── README.md
├── requirements.txt
├── .env.example
├── .gitignore
├── src/
│   ├── __init__.py
│   ├── config.py
│   ├── models.py
│   ├── llm_client.py
│   ├── prompts.py
│   ├── one_shot.py
│   ├── workflow.py
│   └── evaluate.py
└── data/
    └── test_cases.json
```

## 4. Результаты сравнения и основные выводы

### 4.1. Результаты сравнения

**Тестовый набор:** 12 примеров (`data/test_cases.json`), включая неоднозначные (№8, №9, №12) и нестандартные (№11 — отзыв без явных аспектов).

**Способ оценки качества:**
- **Общая тональность** — accuracy (совпадение с эталоном).
- **Извлечение аспектов** — F1 по названиям аспектов (регистронезависимое сравнение по вхождению подстроки).
- **Успешность** — получен валидный JSON и заполнены все обязательные поля.
- **Производительность** — среднее время, число LLM-вызовов, средний расход токенов (из `usage` ответа DeepSeek).

**Условия эксперимента:** модель `deepseek-chat`, `temperature=0`, один прогон по 12 кейсам. Дата: 2026-11-11.

| Метрика | One-shot | Workflow |
|---|---|---|
| Доля успешных выполнений | 1.00 | 1.00 |
| Accuracy (общая тональность) | 0.917 (11/12) | 0.917 (11/12) |
| F1 (извлечение аспектов) | 0.819 | 0.875 |
| Среднее время выполнения, с | 1.50 | 2.73 |
| Среднее число LLM-вызовов | 1.0 | 2.0 |
| Средний расход токенов | 420 | 775 |

**Показательный случай: обе архитектуры ошиблись одинаково (кейс №8).**

Текст: «Цена/качество — супер. Единственное, курьер опоздал на 5 минут.»

Эталон: `overall_sentiment = positive` — отзыв в целом положительный, а опоздание курьера подано как минорное замечание.

Результат обеих архитектур: `overall_sentiment = mixed`, аспекты `['цена/качество', 'доставка']`.

Обе модели зафиксировали наличие негативного сигнала («опоздал») и механически объединили его с позитивом в `mixed`, не распознав маркер минорности «Единственное… на 5 минут». Это **семантическая**, а не архитектурная ошибка: декомпозиция на шаги не помогает, потому что проблема — в интерпретации интенции автора, а не в структуре извлечения. Обе архитектуры допустили одну и ту же ошибку на одном и том же кейсе, что подтверждает: Sequential улучшает структурную часть задачи, но не устраняет ошибки понимания неоднозначного текста.

**Где workflow выиграл (кейс №5).**

Текст: «Курьер опоздал на час, но товар отличный. В целом рекомендую.»

Эталон аспектов: `["доставка", "качество"]`.

- One-shot: `['доставка', 'товар']` — второй аспект назван слишком обще («товар»), не совпал с эталонным «качество».
- Workflow: `['доставка', 'качество']` — оба аспекта совпали с эталоном, F1 на кейсе = 1.0.

Причина — **стабильность номенклатуры**: отдельный промпт Extraction с требованием коротких каноничных названий тем даёт более предсказуемые имена аспектов. Это же видно на кейсе №9: one-shot добавил лишний аспект «общее впечатление» (F1 = 0.667), а workflow вернул ровно `['упаковка']` (F1 = 1.0).

**Где workflow проиграл (кейс №6).**

Текст: «Пользуюсь месяц, полёт нормальный. Батарея держит хорошо.»

Эталон аспектов: `["качество", "батарея"]`.

- One-shot: `['батарея']` — один аспект, но оба совпали бы, если бы модель добавила «качество»; фактически F1 = 0.667 (precision 1.0, recall 0.5).
- Workflow: `['время использования', 'батарея']` — «время использования» лишний, не совпал с «качество»; F1 = 0.5 (precision 0.5, recall 0.5).

Декомпозиция не всегда помогает: шаг Extraction иногда добавляет «описательные» аспекты («время использования»), которых нет в эталоне, и precision падает. Это ограничение выбранного промпта шага 1, а не архитектуры как таковой: более строгий список разрешённых тем (или few-shot с примерами) снизил бы такие ошибки. В среднем по набору выигрыш workflow всё же положительный (F1 0.819 → 0.875), но он не универсален.

### 4.2. Основные выводы

1. **Улучшилось ли качество при переходе к workflow?**
   Частично. Точность общей тональности осталась одинаковой — 0.917 (11/12) у обеих
   архитектур: обе модели ошиблись на одном и том же кейсе №8, не распознав минорность
   замечания о курьере. F1 извлечения аспектов вырос с 0.819 до 0.875 (+6.8%):
   отдельный шаг Extraction с требованием каноничных названий тем даёт более стабильную
   номенклатуру аспектов. Однако выигрыш не универсален: на кейсе №6 workflow добавил
   лишний описательный аспект «время использования» и проиграл one-shot по precision.
   То есть декомпозиция помогает там, где задача структурная (извлечение и нормализация),
   но не компенсирует ошибку интерпретации интенции автора и иногда страдает от
   «переусердствования» на шаге Extraction.

2. **Как изменилась производительность и стоимость?**
   Время выросло в 1.82 раза (1.50 → 2.73 с), число вызовов — с 1 до 2, расход токенов —
   в 1.85 раза (420 → 775). Плата за декомпозицию предсказуема и объяснима: шаг 2 получает
   на вход не только отзыв, но и структурированный список аспектов. Для сценариев, где
   важна стабильность извлечения тем (аналитика по темам, приоритизация негатива),
   обмен оправдан; для массовой обработки простых отзывов достаточно one-shot.

3. **Какие ошибки возникают и как влияют на результат?**
   - **One-shot:** пропуск или «сглаживание» неоднозначной тональности; нестабильные названия аспектов (синонимы, не совпадающие с эталоном); редкие невалидные JSON (обрабатываются retry и fallback).
   - **Workflow:** накопление ошибки — неверное извлечение на шаге 1 не исправляется шагом 2. Плюс: ошибку легко локализовать. DeepSeek в JSON-режиме может вернуть пустую строку — обрабатывается повторной попыткой и fallback-объектом.

4. **Оправдана ли архитектура?**
   Да. Для задачи с двумя логически самостоятельными операциями Sequential даёт прозрачность, тестируемость, локализуемость ошибок и основу для расширения без переработки кода. Основной выигрыш — в стабильности извлечения аспектов; для общей тональности разницы на данном наборе нет.

5. **Ограничения текущей реализации и что необходимо улучшить:**
   - Нет кэширования повторяющихся запросов.
   - Нет асинхронности — независимые вызовы можно выполнять параллельно.
   - Нет автоматической валидации схемы на стороне API (только Pydantic после парсинга).
   - Ошибки интерпретации неоднозначных текстов (кейс №8) требуют более сложных промптов или дополнительных шагов.

## 5. Предполагаемые направления развития системы

- **Routing** — предварительная классификация отзыва как «простой» / «сложный» с выбором one-shot или полного workflow (снижение стоимости без потери качества).
- **Parallel** — параллельная классификация аспектов на шаге 2 для ускорения при большом числе аспектов.
- **Chain-of-Thought / few-shot на шаге 2** — для корректной интерпретации неоднозначных и смешанных отзывов (кейс №8).
- **RAG** — генерация рекомендаций на основе базы знаний компании.
- **Structured Outputs** — переход на строгие JSON-схемы на стороне API для повышения надёжности.
- **Агентная проверка** — верификация фактов в отзыве и автоматическое создание тикетов в CRM.
- **Память и оценка качества** — накопление истории обработок и автоматическая метрика качества на размеченных данных.
